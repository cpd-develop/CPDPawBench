## 3. 合规判定

- **QwenPaw 核心目录**：本特性对 QwenPaw 仓库**零改动**——插件代码在本仓库 `plugins/pawbench-eval/`，经官方 `qwenpaw plugin install <路径>` 装进各人的 `~/.qwenpaw/plugins/`，用的是扩展点而不是插槽缺失（先例 `plugins/apps/agent-kanban/`），因此不触发"审批人 杨严兵/焦笑/杨洋"流程。若 M3 实施中发现必须改 `src/qwenpaw/` 或 `console/src/` 非 cpd 部分才能跑通，必须先按四路判定提审批，不得从"用户说要集成"推断已批准。
- **前端设计系统**：看板是新增页面（提交表单 / 队列 / 结果 / 详情四级区块），适用 `qwenpal-design-system.md` 三条硬约束 + PR 团队块第四行声明。这里补一句免得有人拿"D20 之后代码不在 `console/` 下了"当豁免理由：规则判的是**新增页面与表单、表格、卡片、主题色**，插件 `ui/index.js` 经 `window.QwenPaw` SDK 渲染的就是 console 页面，路径在哪个仓库不影响适用性。
- **本仓库（PawBench）**：按 D23 把 `cpd-extension-over-core-edit.md` 的边界从 QwenPaw 一侧**平移到本仓库**——规则原文只写了 `src/qwenpaw/cpd/` 与 `console/src/cpd/`，这里同构地立 `pawbench/cpd/<feature>/`，理由与原文一致（要持续合并第三方更新）。M1 实测结果比 design §2.1 的原计划更干净：**对核心的改动是零处**，不是"一处依赖块"——依赖改由 `pawbench/cpd/acp_remote_eval/requirements.txt` 自己声明，`pyproject.toml`、`requirements.txt`、`pawbench/agents/factory.py`、`run_bench.py`、`data/pawbench-v1.0/**` 全部未动（H3 原样输出见 `test_` §4.3）。代价是安装本特性时需要显式 `pip install -r` 那一份，而不是装好仓库就够用；这一行必须进 README 的服务启动章节，否则下一个人只会撞到 `ImportError`。若 M2 实施中发现绕不开某处核心改动，按规则的四路判定先提审批（审批人 杨严兵/焦笑/杨洋任一人）并在本节登记，**不从"用户说要加 cpd"推断已批准改核心**。
- **"每特性四份文档"规则的登记**（D16 + D20）：本仓库这四份一份不裁。曾按"跨仓库交付"登记过对 QwenPaw 仓库侧的裁剪（裁的是那边的四份、理由是两处各维护必然分叉、内容并入本目录 + 那边 README 放指针）；D20 之后**裁剪本身消失**——插件代码与文档同在本仓库，QwenPaw 仓库不接收任何交付物，那条规则在这个特性上没有作用对象。留这段是为了让下一个人不必再去查"是不是还要在 QwenPaw 那边补文档"：不用。插件 README（本仓库 `plugins/pawbench-eval/README.md`）仍只放安装两步 + 一行指向 `pal_sdd/feat_acp_remote_eval/`，不复制内容。

一句话结论：acp-remote-eval 是 PawBench 的旁挂扩展，不是改造或分叉。它复用核心的 BaseAgent 生命周期、TaskLoader 题库格式、grader 判分语义共 3 处；把「一次性 CLI + 我们提供的容器」换成「常驻服务 + 对方自带环境（BYO）+ 自建 HTTP 数据面」。run_bench.py 不 import 它，它也不 import CLI —— 只跑本地 benchmark 的安装完全不受影响。
两者是什么关系？

扩展，不是分叉。整个特性对核心的依赖只有 3 条绿边（BaseAgent / TaskLoader / 判分 helper），核心源码与共享依赖零改动。灰虚线是「绕过不调用」：CLI 编排、容器环境、AgentFactory 注册、grade_task 入口。红虚线是尚未建成的看板（M3）、MCP + 出题 skill（M4）与判分沙箱，不是现状能力。

同一道题，两条链路各走什么步骤？

左=原有本地链路，右=新增远端链路，中列标出该阶段的差异性质。②选题与⑧判分语义完全复用；④运行环境是根本差异（我们提供环境 → 对方自带环境 BYO），⑤⑥⑦因此全部改写；⑩是这条差异的代价：结果按 by_environment 单独分档。

文件怎么过去、产物怎么回来、分怎么打？

紫边是跨信任边界的两条唯一通道：ACP 下发 manifest，HTTP 数据面回收产物。第 8 步（对方机器内部执行）对我们不可观测，只有 ACP session/update 与最终上传可见。第 12 步的 exec 目前仍在服务进程内 —— 判分沙箱未建，这是已知缺口而非现状保障。
